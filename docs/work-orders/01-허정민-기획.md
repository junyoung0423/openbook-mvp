허정민 님의 산출물은 **다른 사람이 코드를 완성했다고 판단하는 기준**이 됩니다. 계산 규칙이 모호하면 박다연 님의 계산 엔진이 틀려도 틀렸는지 알 수 없고, 사례 계약서가 없으면 정준영 님의 조건 추출 정확도를 알 수 없습니다. 그래서 **이 3가지가 늦어지면 전체가 멈춥니다.**

## 이슈 #5 — 계산 규칙 명세서와 손계산 테스트 케이스 (가장 먼저)

https://github.com/junyoung0423/openbook-mvp/issues/5

### 의도
박다연 님이 만드는 계산 엔진(M5)은 **허정민 님이 정한 규칙을 그대로 코드로 옮깁니다.** 규칙을 애매하게 쓰면 엔진 담당자가 추측해서 만들고, 그 추측이 틀리면 작가에게 틀린 금액을 보여 줍니다. 그래서 "정답이 되는 숫자"를 손으로 계산해서 JSON으로 남겨야 합니다. 엔진은 이 케이스와 **100% 일치**해야 완성입니다.

### 기본 모델 (명세서 4절 M5)
MG를 RS 정산액에서 회수하는 구조입니다. 월(기간) `t`마다:

```
S_t = r × (G_t − D_t)            작가 몫 (RS)
P_t = max(0, S_t − B_{t−1})      지급액
B_t = max(0, B_{t−1} − S_t)      남은 미회수 MG   (B_0 = MG 금액)
```
`G` = 총매출, `D` = 계약서가 정한 공제 합계, `r` = RS율. 이 모델은 **출발점**이며, 아래 "정해야 할 것"을 규칙으로 확정해야 합니다.

### 산출물
1. `docs/calc-rules.md` — 계산 규칙 명세서 (아래 "정해야 할 것" 전부에 답이 적혀 있어야 함)
2. `docs/calc-cases/*.json` — 손계산 테스트 케이스 (최소 12개, 아래 목록)

### 정해야 할 것 (하나라도 비면 엔진 담당자가 추측하게 됩니다)
| # | 질문 | 왜 중요한가 |
|---|---|---|
| R1 | 공제율(예: 결제 수수료 10%)은 **어떤 금액에** 곱하는가? 총매출? 순매출? | 같은 계약서에서도 금액이 달라짐 |
| R2 | `revenue_base`가 `net`(순매출)일 때 `G − D`는 어떻게 정의하는가? 공제를 **두 번 빼지 않도록** 어떻게 하는가? | 샘플 계약서처럼 순매출 정의와 공제 조항이 겹치는 경우가 실제로 있음 |
| R3 | 원 미만 처리: 절사 / 반올림 / 올림 중 무엇이고, **어느 단계에서** 적용하는가 (S, P, 공제 각각)? | 엔진과 정답이 1원 차이로 어긋남 |
| R4 | `mg_recoup`가 `separate`(RS와 별도)일 때 P는? (회수 없음 → `P = S` 인가?) MG 자체의 지급은 대조 대상인가? | 회수형/비회수형 분기 |
| R5 | 매출이 0원이거나 음수(환불)인 달은? | 경계 조건 |
| R6 | 회수 중간에 `S`가 `B`와 정확히 같으면? (`P = 0`, `B = 0`) | 경계 조건 |
| R7 | 정산서 지급액과 비교할 값은 `P`인가? 차이 부호는? (명세서: 차이 = 계약서 기준 금액 − 정산서 금액) | 결과 화면의 핵심 숫자 |
| R8 | `mg_carryover`(미회수분 이월·환수)는 MVP에서 계산에 반영하는가, 표시만 하는가? | 범위 |
| R9 | 여러 달을 한 번에 입력할 때, 이전 달의 `B`는 어디서 가져오는가? (첫 입력 달이 계약 첫 달이 아닐 수 있음) | 상태 이어받기 |
| R10 | `계산 불가`가 되는 조건의 목록 (구간별 RS, 복수 매체 합산, 필수 조건 누락 등)과 사용자에게 보일 이유 문구 | 추측해서 계산하지 않는 원칙 |

> 정하기 어려운 항목은 **"결정 필요"로 이슈에 올리고** 임시 안과 이유를 적어 주세요. 비워 두는 것이 가장 나쁩니다.

### 테스트 케이스 형식 (이 형식 그대로, 값은 모두 문자열)
금액은 원 단위 문자열, 비율은 0~1 문자열입니다. 아래는 **형식을 보여 주는 예시**이며 실제 계약 값이 아닙니다.

```json
{
  "case_id": "mg-recoup-partial-01",
  "description": "MG 회수 중: 첫 달은 전액 회수에 쓰이고 지급 0, 둘째 달에 남은 MG를 회수하고 나머지를 지급",
  "terms": {
    "mg_amount": "5000000",
    "mg_recoup": "from_rs",
    "rs_rate": "0.6",
    "revenue_base": "gross",
    "deductions": [{"name": "결제 수수료", "rate": "0.1", "amount": null}]
  },
  "periods": [
    {
      "period": "2027-01",
      "gross": "3000000",
      "reported_payout": "0",
      "expected": {
        "deduction_total": "300000",
        "share": "1620000",
        "recouped": "1620000",
        "mg_balance_after": "3380000",
        "payout": "0",
        "diff": "0"
      }
    },
    {
      "period": "2027-02",
      "gross": "10000000",
      "reported_payout": "2000000",
      "expected": {
        "deduction_total": "1000000",
        "share": "5400000",
        "recouped": "3380000",
        "mg_balance_after": "0",
        "payout": "2020000",
        "diff": "20000"
      }
    }
  ],
  "unsupported_reason": null
}
```
- `expected`의 모든 값은 **손(또는 계산기)으로 직접 계산**한 정답입니다. 코드로 만든 값을 정답으로 쓰면 안 됩니다 (엔진 버그가 그대로 정답이 됩니다).
- 계산 불가 케이스는 `expected` 대신 `"unsupported_reason": "구간별 RS는 지원하지 않습니다"`처럼 사유를 적습니다.

### 필수 케이스 목록 (최소)
1. MG 회수 전 (첫 달, 지급 0)
2. MG 회수 중 (여러 달 연속)
3. MG 회수 완료 직후 달 (일부만 회수하고 나머지 지급)
4. `S = B` 경계 (R6)
5. 정률 공제
6. 정액 공제
7. 공제 없음
8. 매출 0원인 달
9. `revenue_base = gross`
10. `revenue_base = net` (R2의 규칙 적용)
11. `mg_recoup = separate` (비회수형)
12. 계산 불가 (구간별 RS)
13. 정산서 지급액이 계약서 기준과 같은 경우 (차이 0)
14. 정산서 지급액이 더 적은 경우 / 더 많은 경우 (차이 부호 확인)

### 끝나는 기준 (이슈 #5)
- [ ] R1~R10 모두 답이 적혀 있다 (결정이 안 된 항목은 "결정 필요"와 임시 안)
- [ ] 케이스 14종 이상이 JSON으로 있고, 모든 정답을 손으로 계산했다
- [ ] 박다연 님이 읽고 "추측할 부분이 없다"고 확인했다

## 이슈 #4 — MG·RS 계약 유형 분류

https://github.com/junyoung0423/openbook-mvp/issues/4

### 의도
스키마의 선택지 일부는 명세서에 값이 없어 **정준영 님이 임시로 정한 것**입니다. 실제 계약 유형을 보고 맞는지 확정해야 합니다. 이 선택지가 틀리면 조건 추출과 계산 엔진, 화면이 모두 틀린 선택지를 가지고 움직입니다.

### 산출물
`docs/contract-types.md` — 첫 대상 분야(웹툰·웹소설)에서 실제로 나오는 MG·RS 구조 목록

### 확인·결정 요청
| # | 항목 | 현재 임시 값 | 요청 |
|---|---|---|---|
| D1 | `mg_carryover` (미회수분 처리) | `carry_over`(이월) / `refund`(환수) / `forgiven`(반환 요구 없음) / `unknown` | 실제 계약에서 나오는 유형에 맞게 확정 |
| D2 | `settlement_cycle` (정산 주기) | `monthly` / `quarterly` / `semiannual` / `other` | 확정 |
| D3 | `mg_pay_date`, `payment_day` | 계약서 문구 그대로의 문자열 | 날짜 규칙(예: "다음 달 10일", "정산서 제공 후 15일 이내")을 구조화할지, 문자열로 둘지 결정 |
| D4 | 구간별 RS, 복수 매체 합산 | 스키마에는 있으나 계산하지 않음(`계산 불가`) | MVP에서 **계산할지** 결정. 실제 계약에서 얼마나 자주 나오는지 근거와 함께 |
| D5 | `revenue_base` 정의가 한 계약 안에서 충돌하는 경우 | 사용자가 원문을 보고 고름 | 어떤 충돌 유형이 흔한지 사례 정리 |

### 끝나는 기준 (이슈 #4)
- [ ] 계약 유형 목록 문서가 있다
- [ ] D1~D5가 결정되어 PR #1(스키마)에 반영되었다 (선택지가 바뀌면 PR #1에 코멘트)
- [ ] 구간별 RS·복수 매체 합산을 MVP에 넣을지 결정이 이슈에 기록되었다

## 이슈 #3 — 사례 계약서·정산서 확보와 익명화

https://github.com/junyoung0423/openbook-mvp/issues/3

### 의도
지금까지의 모든 정확도 확인은 **가상 계약서 2건**으로 한 것입니다. 실제 계약서에서는 표기가 훨씬 다양해서 결과가 다를 수 있습니다. 실제 사례가 없으면 "조건 추출이 얼마나 맞는지"를 말할 수 없습니다 (명세서도 `정확도 N%` 같은 문장을 쓰지 말라고 했습니다).

### 규칙 (어기면 법적 문제)
- 실제 계약서·정산서는 **git에 올리지 않습니다.** `data/private/`에만 둡니다 (git이 무시함). 메신저·이메일로 공유할 때도 익명화한 것만 보냅니다.
- **익명화 범위**: 실명, 연락처, 주소, 계좌번호, 주민등록번호, 작품명, 회사명을 지웁니다. 금액·비율·조항 구조는 남깁니다.
- 제공자에게 **익명화 조건과 사용 목적**(개발·평가 용도)을 알리고 동의를 받습니다.
- 계약서가 외부 서비스(Upstage)로 전송되는 평가에 쓰일 수 있음을 제공자에게 알립니다.

### 끝나는 기준 (이슈 #3)
- [ ] 확보한 건수와 출처(익명화 조건 포함)를 팀에 공유했다
- [ ] 실제 자료는 `data/private/`에만 있고 레포에는 없다
- [ ] 정산서 사례가 있다면 형식(표 모양, 항목 이름)을 정리했다 — **정산서 입력 화면 설계에 필요**
- [ ] 사례가 없다면 그 사실과 대안(가상 사례를 몇 건 더 만들기)을 이슈에 기록했다
