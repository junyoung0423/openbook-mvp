## 전시준 님 일의 의미

이 서비스는 계산 결과를 **판단 없이** 보여 주는 서비스입니다. 디자인이 색이나 아이콘으로 "좋음/나쁨"을 암시하면, 글에서 아무리 판단을 안 해도 서비스의 원칙이 깨집니다. 그리고 핵심 화면 둘(**조건 확인**, **대조 결과**)이 제품의 신뢰를 정합니다. 작가가 "내 계약서의 어느 조항에서 이 숫자가 나왔는지"를 한눈에 알아야 합니다.

## 받는 즉시 할 일 (순서대로)

## 이슈 #11 — 전체 흐름 와이어프레임

https://github.com/junyoung0423/openbook-mvp/issues/11

### 의도
신민주 님(프론트)이 구현하기 전에 **화면의 정보 구조와 상태**를 정합니다. 화면 상태가 빠지면 구현 단계에서 개발자가 임의로 만들게 되고, 그 임의 선택이 원칙을 깹니다.

### 흐름
`업로드 → 조항 확인 → 조건 확인 → 정산서 입력 → 대조 결과` (그리고 삭제, 오류·빈 상태)

### 화면별 필수 요소

**1. 업로드**
- 입력 방식: PDF, docx, HWP, 사진·스캔, 본문 붙여넣기
- **개인정보 안내와 동의** (동의해야 업로드 가능): 실명·연락처·계좌가 있을 수 있고, 계약서 내용이 외부 서비스(Upstage Document Parse, Solar Pro 4)로 전송됨을 알림. 문구는 신민주·허정민 님과 정합니다.
- 처리 중 상태 (처리는 시간이 걸립니다)

**2. 조항 확인**
- 나뉜 조항 목록. **불확실 상태**(`clause_review_needed`): "자동으로 나눈 결과를 확인해 주세요" + 조항을 합치기·나누기·번호/제목 수정
- **실패 상태**(조항을 하나도 못 나눔): 직접 나누기 또는 본문 붙여넣기 안내

**3. 조건 확인 (가장 중요)** — 한 화면에 아래가 모두 보여야 합니다
- 조건 항목마다: 이름, 값, **상태 라벨(`추출됨` / `찾지 못함` / `직접 입력`)**, **근거 조항 번호와 원문 인용**, 값을 고치는 입력
- `찾지 못함` 항목: 직접 입력을 유도하는 상태. 입력 전에는 확정 불가가 **시각적으로** 보여야 함
- 경고(`warnings`) 영역: 사용자가 확인해야 할 점
- 해석이 갈리는 정의(총매출/순매출)를 **계약서 문구를 보고 고르는** 방식
- **"확정" 버튼**: 사용자가 명시적으로 누름. 확정 전과 후의 상태가 구분됨
- 확정 전에는 다음 단계(정산서 입력·대조)가 막혀 있음이 분명해야 함

**4. 정산서 입력**
- 정산 기간, 총매출, 공제 항목, 정산서에 적힌 지급액
- 같은 계약서에 **기간별로 여러 번** 입력·목록 관리
- (표 붙여넣기 UI는 입력 형식이 정해진 뒤에 추가합니다)

**5. 대조 결과 (가장 중요)** — **차이와 근거 조항이 한눈에 보이게**
- 가장 큰 **세 숫자**: 계약서 기준 금액 / 정산서 금액 / 차이
- 결과 문장: `계약서 기준으로 계산하면 ○○원, 정산서에는 △△원, 차이는 □□원입니다.`
- 계산 단계별 내역 + **각 단계의 근거 조항 연결** (단계를 누르면 조항 원문)
- **플랫폼에 확인할 질문 목록**
- 고정 문구 영역: "이 결과는 사용자가 확정한 조건에 대한 계산입니다", 근거 조항, 기준일, 전문가 상담 안내
- `계산 불가` 상태: 이유 표시, 추정 금액 없음

**6. 삭제**: 계약서·정산 기록 삭제, **되돌릴 수 없음** 확인

### 모든 화면에 필요한 상태 (빠뜨리지 마세요)
빈 상태 / 로딩(처리 중) / 오류(다시 시도) / 부분 실패(조항은 있고 조건 추출 실패) / 확정 전 / 확정 후

### 디자인 제약 (반드시)
| 제약 | 이유 |
|---|---|
| **색·아이콘·점수로 좋고 나쁨을 표현하지 않는다.** 차이가 있다고 빨강, 없다고 초록 같은 것 금지. 위험도 게이지·신호등·점수 금지 | 서비스는 판단하지 않는다 |
| 차이는 **숫자와 글로만** 보여 준다 (부호는 `계약서 기준 − 정산서`) | 판단 표현 금지 |
| `찾지 못함`을 **"문제없음/표준과 같음"처럼 안심하게 보이는 모양**(체크 표시, 초록색)으로 만들지 않는다 | 사용자가 오해함 |
| 상태 라벨 이름은 `추출됨` / `찾지 못함` / `직접 입력`으로 고정 | 개발·문서와 일치 |
| 문구에 **위반, 부당, 불리, 유리, 위험도 점수, AI가 새로 쓴 수정 문구**를 쓰지 않는다 (버튼, 툴팁, 안내문 포함) | 법적 안전장치 |
| 모든 결과·답변 영역에 **근거 조항, 기준일, 전문가 상담 안내** 자리를 둔다 | 명세서 원칙 |
| **모바일 반응형**: 웹앱을 모바일 폭에서도 쓸 수 있어야 한다 | 명세서 (Next.js 반응형) |
| 실제 계약서·개인정보가 들어간 캡처를 디자인 파일에 넣지 않는다 | 개인정보 |

### 실제 데이터 길이를 반영하세요
`docs/mock/process_result_ok_sample_a.json`의 조항 원문, 인용문(`quote`), 경고 문장이 **실제로 얼마나 긴지** 보고 레이아웃을 정합니다. 짧은 가짜 문구로만 만들면 구현 때 깨집니다. 특히:
- 인용문이 여러 줄이고 `1. …\n2. …` 같은 목록을 포함할 수 있습니다
- 공제 항목은 **목록**이고, 항목마다 비율 또는 정액입니다
- 구간별 RS 값은 목록 형태입니다 (계산은 하지 않지만 표시될 수 있음)
- 한 조건 항목에 값이 비어 있는 경우(`찾지 못함`)가 흔합니다 (샘플 B는 9개 중 3개)

### 산출물
- 전체 흐름 와이어프레임 (위 6개 화면 + 상태들). 도구는 자유(Figma 권장)이며 **링크를 이슈 #11에 올립니다**
- 문구 초안: 개인정보 동의, 경고, 오류, 삭제 확인 (판단 표현 금지 규칙 적용)

### 끝나는 기준 (이슈 #11)
- [ ] 6개 화면의 와이어와 위 "모든 화면에 필요한 상태"가 있다
- [ ] 조건 확인 화면에 **상태 3종과 근거 조항 원문이 한 화면에** 보인다
- [ ] 대조 결과 화면에 **계약서 기준 금액, 정산서 금액, 차이, 근거 조항**이 보인다
- [ ] 금지 표현과 색으로 하는 판단 표현이 없다
- [ ] 신민주 님이 보고 "구현할 때 추측할 부분이 없다"고 확인했다

## 3단계 (나중에)
입구 화면(표준계약서 비교 요약, 조항 Q&A), 랜딩 페이지, 데모 시나리오. 이슈가 열리면 따로 안내합니다.

## 하지 말 것
- 판단을 암시하는 색·아이콘·점수를 쓰지 않는다
- 데이터 길이를 무시한 짧은 가짜 문구로만 레이아웃을 정하지 않는다
- 정해지지 않은 화면(표 붙여넣기 UI)을 혼자 확정하지 않는다
- 사용자 앞에서 숫자를 다르게 보여 주는 디자인(반올림해서 줄여 표시 등)을 하지 않는다 — 서버가 준 숫자를 그대로 보여 준다

## 막힐 만한 곳과 먼저 묻기
| 상황 | 해야 할 일 |
|---|---|

| 문구에 판단 표현이 섞이는지 애매함 | 허정민 님(기획)에게 질문 |
| 구현이 어려운 디자인 | 신민주 님과 이슈에서 조율 |
