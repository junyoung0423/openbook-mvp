## 신민주 님 일의 의미

사용자가 서비스에서 만나는 모든 것이 신민주 님의 화면입니다. 이 서비스는 **"작가가 조건을 직접 확인하고 확정한다"**가 핵심이라, 조건 확인 화면이 제품의 신뢰를 정합니다. 화면이 값을 잘못 보여 주거나, 추출된 값을 확인 없이 넘기게 만들거나, 판단하는 말투를 쓰면 서비스의 원칙이 깨집니다.

백엔드가 완성되기 전에는 **목 데이터로 먼저 개발**합니다. 목 데이터는 실제 모델이 낸 결과를 담은 파일이라, 이 모양대로 만들면 나중에 연결이 쉽습니다.

**업로드 화면 필수 요소:**

**끝나는 기준:** `npm run dev` 실행 / 목 데이터로 업로드 → 조항 확인 화면 이동 / 위 4가지 상태가 모두 화면으로 만들어짐 / 스키마 머지 후 `docs/schemas/*.schema.json`으로 타입 생성

## 2단계 (스키마 PR #1 머지 후 이슈가 열립니다)

### 조건 확인·수정 화면 (가장 중요)

**한 화면에 있어야 하는 것 (조건 항목마다):**
1. 항목 이름 (예: MG 금액, RS 배분율, 공제 항목…)
2. **값**
3. **상태 라벨**: `추출됨` / `찾지 못함` / `직접 입력` (이름 변경 금지)
4. **근거 조항**: 조항 번호와 **원문 인용(`quote`)**. 원문은 그대로 보여 줍니다 (줄이거나 요약하지 않음). 조항 전체 원문도 볼 수 있어야 합니다.
5. 값을 **고칠 수 있는 입력**. 고치면 상태가 `직접 입력`으로 바뀝니다.

**동작 규칙 (모두 필수):**
- 사용자가 **명시적으로 "확정"을 눌러야** 다음 단계로 갑니다. 자동 확정 금지, 기본 체크된 확정 금지.
- `찾지 못함` 항목은 **값을 입력하기 전에는 확정할 수 없습니다.**
- `찾지 못함` 옆에 "표준과 같음", "문제없음", "해당 없음" 같은 말을 쓰지 않습니다.
- `warnings` 배열의 문장은 **눈에 띄게 그대로** 보여 줍니다 (예: "비율·금액이 정해지지 않은 공제 항목은 … 직접 입력하세요: 마케팅 비용").
- **해석이 갈리는 정의**: `revenue_base`(총매출/순매출)처럼 계약서 안에서 조항마다 말이 다를 수 있는 항목은, **계약서 문구를 보여 주고 사용자가 고르게** 합니다. 추출된 값을 맞는 것처럼 보여 주지 않습니다 (샘플 A가 실제로 이런 경우입니다).
- `confirmed`는 서버가 항상 `false`로 줍니다. 확정은 사용자의 확정 동작(`PUT /contracts/{id}/terms`)으로만 `true`가 됩니다.

**`process_contract` 결과에 따른 화면 분기:**
| 필드 | 화면 |
|---|---|
| `clause_review_needed = true` | 조항 확인 화면에서 **나뉜 조항을 사용자가 고칠 수 있게** (합치기, 나누기, 제목·번호 수정). 확인하기 전에는 조건 확인으로 보내지 않음 |
| `clauses = []` | 조항 직접 나누기 또는 본문 붙여넣기 안내 |
| `terms = null` + `error` | 조항은 보여 주고, "조건 추출에 실패했습니다" + **다시 시도** + **직접 입력으로 계속** |
| `warnings` 있음 | 위 규칙대로 표시 |

### 정산서 입력 화면
- 정산 기간, 총매출, 공제 항목, **정산서에 적힌 지급액**을 입력합니다. 같은 계약서에 **기간별로 여러 번** 입력할 수 있습니다.
- **직접 입력 폼을 먼저 구현합니다.** 표 붙여넣기는 형식이 정해지지 않았습니다 (정산서 사례 확보 이슈 #3 이후) — 정해지기 전에는 만들지 않습니다.

### 대조 결과 화면
- 가장 크게 **세 숫자**: 계약서 기준 금액 / 정산서 금액 / 차이. 숫자는 서버가 준 값을 **그대로** 표시합니다.
- 결과 문장은 서버가 준 문장을 그대로 씁니다: `계약서 기준으로 계산하면 ○○원, 정산서에는 △△원, 차이는 □□원입니다.`
- 계산 단계별 내역(어떤 조건을 썼는지)과 **근거 조항 연결**: 단계를 누르면 해당 조항 원문이 보입니다.
- **플랫폼에 확인할 질문 목록**을 함께 보여 줍니다.
- 화면에 **"이 결과는 사용자가 확정한 조건에 대한 계산입니다"**를 적습니다. 근거 조항, 기준일, 전문가 상담 안내를 붙입니다.
- `계산 불가`일 때는 이유를 그대로 보여 줍니다. 추정 금액을 만들어 보여 주지 않습니다.
- 차이가 있다/없다에 **색 신호(빨강·초록)나 아이콘으로 좋고 나쁨을 표현하지 않습니다.**

### 삭제 화면
- 계약서와 정산 기록을 삭제하는 기능. 지워지는 것과 **되돌릴 수 없음**을 확인받습니다.

## 숫자·데이터 처리 규칙 (오류가 가장 많이 나는 곳)

- **금액·비율은 문자열로 받습니다.** `"5000000"`, `"0.6"`.
- **JavaScript `Number`로 변환해 계산하지 않습니다.** 프론트는 **금액을 계산하지 않습니다.** 서버가 준 숫자를 보여 주기만 합니다.
- 표시할 때만 포맷합니다: `"5000000"` → `5,000,000원`, `"0.6"` → `60%`. **문자열 기반으로 포맷**하고(예: 천 단위 콤마를 문자열 조작으로), 어쩔 수 없이 계산이 필요하면 `decimal.js` 같은 십진 라이브러리를 씁니다.
- 입력 칸에서 사용자가 쓴 금액·비율도 **문자열로** 서버에 보냅니다. 비율을 입력받을 때 `60`(퍼센트)을 `"0.6"`으로 바꾸는 변환은 한 곳에서만 하고 테스트합니다.
- 선택값(`from_rs`, `net` 등)은 영문 값 그대로 주고받고, **화면 표시 이름만** 한글로 매핑합니다. 선택지 목록은 하드코딩하지 말고 `docs/schemas/*.schema.json`에서 읽습니다 (`mg_carryover`, `settlement_cycle` 선택지는 아직 확정 전입니다).
- 타입은 `docs/schemas/*.schema.json`으로 생성합니다. 손으로 따로 타입을 만들면 스키마가 바뀔 때 어긋납니다.
- API 오류는 `error`·오류 코드를 **그대로** 사용자에게 이해되는 문장으로 바꿔 보여 줍니다. 확정 전에 대조를 요청하면 서버가 오류 코드로 거절합니다(코드 이름은 박다연 님과 합의, 예: `TERMS_NOT_CONFIRMED`). 화면은 애초에 확정 전에는 대조 버튼을 막아야 합니다.

## 문구 규칙 (화면의 모든 글자에 적용)
- 쓰지 않는 말: **위반, 부당, 불리, 유리, 위험도 점수, AI가 새로 쓴 수정 문구**와 그 유사 표현
- 버튼·툴팁·빈 화면 안내·오류 문구까지 포함합니다. 문구를 새로 만들 때는 전시준 님(디자인)과 정합니다.

## 하지 말 것
- 추출된 값을 사용자가 확인하기 전에 다음 단계로 넘기지 않는다
- 금액을 `Number`로 계산하거나 소수점 반올림하지 않는다
- 서버가 준 `quote`와 조항 원문을 줄이거나 바꿔 보여 주지 않는다
- `찾지 못함`을 "해당 없음/표준과 같음"처럼 보이게 만들지 않는다
- 결과를 색(빨강/초록)이나 점수로 평가하지 않는다
- 정해지지 않은 것(정산서 붙여넣기 형식, 오류 코드 이름)을 혼자 정하지 않는다 → 이슈에 질문
- 목 데이터 JSON을 임의로 고쳐서 쓰지 않는다 (화면이 실제와 어긋남). 필요한 상태가 없으면 정준영 님에게 요청
