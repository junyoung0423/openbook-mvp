## 박다연 님 일의 의미

박다연 님은 **서버, 데이터 저장, 파일 읽기, 계산 엔진**을 맡습니다. 이 서비스에서 **돈 숫자를 만드는 유일한 곳이 계산 엔진**입니다. 엔진이 틀리면 작가에게 틀린 금액을 보여 주고, 그러면 서비스의 신뢰가 끝납니다. 그래서 이 프로젝트에서 가장 엄격하게 만들어야 하는 부분이 박다연 님 몫입니다.

일이 많은 담당입니다. 그래서 **정산서 입력 정규화는 정준영 님이 나눠 받습니다**, 알림(P2)은 뒤로 미룹니다. 부담이 크면 이슈에 바로 알려 주세요.

### 이슈 #8 — Postgres 설정과 DB 모델

https://github.com/junyoung0423/openbook-mvp/issues/8

**의도:** 계약, 조항, 조건, 정산서, 대조 결과가 서로 이어지는 구조를 안전하게 저장합니다. 금액이 저장·조회 과정에서 변하면 안 됩니다.

**테이블 (명세서 5절):**
| 테이블 | 주요 필드 |
|---|---|
| users | id, email, created_at |
| contracts | id, user_id, title, file_ref, status, uploaded_at (status: 처리중 / 조건 확인 대기 / 확정) |
| clauses | id, contract_id, no, title, text, type_id, std_clause_id |
| terms | id, contract_id, key, value, status, source_clause_id, quote, confirmed_at |
| statements | id, contract_id, period_start, period_end, gross, deductions, reported_payout |
| reconciliations | id, statement_id, computed_payout, diff, breakdown, unsupported_reason |
| qa_logs | id, contract_id, question, answer, cited_clause_ids |
| alerts | id, contract_id, due_date, channel, sent_at (P2) |

**제약:**
- 금액은 `NUMERIC`으로 저장하고 `Decimal`로 읽고 씁니다. `float`·`REAL`·`DOUBLE` 금지.
- 비율(`rs_rate`)도 `NUMERIC`입니다 (`0.6`이 `0.5999…`가 되면 안 됨).
- `terms.value`는 항목마다 형식이 다릅니다 (금액, 선택값, 목록). `JSONB`로 저장하고, 읽을 때 **`backend/src/openbook/schemas/terms.py`의 `Term` 모델로 다시 검증**합니다.
- `breakdown`(계산 단계별 내역)도 `JSONB`입니다.
- `confirmed_at`이 있는 값만 "확정"입니다. **확정은 사용자 요청으로만** 기록합니다 (서버가 알아서 확정하지 않음).
- 마이그레이션 도구(Alembic 등)를 정하고 이슈에 선택 이유를 적습니다.
- 로컬 실행 방법(Docker 또는 설치)을 `README`에 문서화합니다.
- 개발 초기에는 **SQLite로 먼저 돌려도 됩니다**. 그 경우 `NUMERIC` 정밀도가 달라지니, Postgres로 옮길 때 금액 왕복 테스트(저장 → 읽기 → 같은 값)를 반드시 추가합니다.

**끝나는 기준:** 로컬 실행 방법 문서화 / 금액 `NUMERIC` / 마이그레이션 도구 선택 / 금액·비율 왕복 테스트

### 이슈 #9 — Upstage Document Parse 연동 (M1)

https://github.com/junyoung0423/openbook-mvp/issues/9

**의도:** PDF, docx, HWP, 사진·스캔 이미지, 붙여넣은 본문을 **한 경로로** 읽어 텍스트로 만듭니다. 이 텍스트가 정준영 님의 조항 분할 입력이 됩니다.

**인터페이스 (고정):** `파일 → 정규화 텍스트 + 요소 위치`. 나중에 파서를 바꿀 수 있도록 Upstage 전용 코드가 인터페이스 밖으로 새지 않게 합니다.

**가장 중요한 연동 제약 (실패하기 쉬운 부분):**
조항 분할기(`split_clauses`)는 **줄 맨 앞에서 시작하는 `제N조`, `N.` 제목 줄**로 조항을 나눕니다. Document Parse가 이렇게 바꿔 놓으면 분할이 실패합니다.
- 제목 줄 앞에 `#`, `**`, `<p>`, `<h2>` 같은 마크업이 붙는 경우
- 줄바꿈 없이 조항이 한 문단으로 이어지는 경우
- 번호와 제목이 표(table) 안에 들어가는 경우

→ **파서 출력은 "줄바꿈이 보존된 평문"으로 정규화해서 넘기세요.** 그리고 **실제 파서 출력을 `split_clauses`에 넣어 조항이 제대로 나뉘는지 확인하는 테스트**를 반드시 추가합니다 (가상 샘플 `data/samples/`를 PDF·docx로 만들어 시험). 표는 정산서 입력에도 쓰이므로 표 정보는 별도로 보존합니다.

**제약:**
- 외부 API 장애·타임아웃·지원하지 않는 형식은 **오류로 명확히 알립니다** (빈 텍스트를 성공으로 돌려주지 않음).
- **로그에 계약서 원문을 남기지 않습니다.**
- API 키는 `.env`의 `UPSTAGE_API_KEY`를 씁니다. 키를 각자 발급받을지 공유할지는 팀에서 정합니다 (공유한다면 메신저 단체방이 아니라 개인 메시지로 전달).
- 가격 기준(쪽당 Standard 0.01달러, Enhanced 0.03달러, 2026-11-09 기준): 테스트로 호출을 많이 하지 않습니다.

**끝나는 기준:** PDF·docx·이미지·붙여넣기 입력 / 평문 + 요소 위치 출력 / 실패·타임아웃 처리 / **파서 출력 → `split_clauses` 연동 테스트**

## 2단계 (스키마 PR #1이 머지된 뒤 이슈가 열립니다)

### API 엔드포인트 (명세서 5절)

| 메서드와 경로 | 설명 | 우선순위 |
|---|---|---|
| `POST /contracts` | 계약서 업로드, 처리 시작 (**비동기**) | P0 |
| `GET /contracts/{id}` | 처리 상태 조회 | P0 |
| `GET /contracts/{id}/clauses` | 조항 분할 결과 | P0 |
| `GET, PUT /contracts/{id}/terms` | 추출 조건 조회, 수정·확정 | P0 |
| `POST /contracts/{id}/statements` | 정산서 입력 | P0 |
| `GET /contracts/{id}/reconciliations` | 대조 결과 조회 | P0 |

**`POST /contracts` 처리 작업은 `process_contract` 하나만 부르면 됩니다:**
```python
from openbook.pipeline import process_contract
from openbook.terms import UpstageClient

result = process_contract(contract_id, text, UpstageClient.from_env())
payload = result.model_dump(mode="json")      # 그대로 저장·응답 가능
```
| 결과 | 서버가 할 일 |
|---|---|
| `clauses`가 있고 `terms`가 있다 | 조항·조건 저장 → contracts.status = `조건 확인 대기` |
| `clause_review_needed = true` | 저장하되 프론트가 조항 확인을 요구할 수 있게 값을 노출 |
| `clauses = []` (`clause_style = "none"`) | 조건 추출 없음. 사용자에게 조항 직접 나누기 또는 본문 붙여넣기 안내 |
| `error`가 있다 | 조항은 저장, 조건은 비워 두고 오류를 노출 (재시도 가능하게) |
| `warnings` | 그대로 저장하고 노출 (사용자가 확인할 점) |

실제 응답 예시는 `docs/mock/`에 있습니다. `process_contract`는 **저장·비동기 처리·진행률을 하지 않습니다** — 그건 API의 일입니다. 조건 추출 실패 시 자동 재시도도 없으니 필요하면 API에서 정책을 정하세요.

**제약:**
- 업로드 처리는 오래 걸릴 수 있어 **비동기**입니다. 프론트는 `GET /contracts/{id}`로 완료를 확인합니다.
- **`PUT /contracts/{id}/terms`에서만 `confirmed`가 바뀝니다.** 요청한 사용자가 확정한 값만 `confirmed=true`와 `confirmed_at`을 가집니다.
- **대조(`reconciliations`)는 조건이 모두 확정된 계약서에서만 실행합니다. 확정 전 요청은 오류 코드로 거절합니다** (예: HTTP 409, 코드 `TERMS_NOT_CONFIRMED`). 오류 코드 이름은 이슈에서 프론트와 합의합니다.
- 사용자는 **자기 계약서만** 볼 수 있습니다 (모든 조회·수정에 `user_id` 확인).
- API는 JSON만 주고받고, 요청·응답 모델은 `schemas/`의 pydantic을 씁니다 (FastAPI 문서가 곧 명세).

### M5 계산 엔진 (가장 엄격하게)

**먼저 필요한 것:** 허정민 님의 **계산 규칙 명세서(이슈 #5)와 손계산 케이스**. 이것이 나오기 전에 규칙을 추측해서 만들지 않습니다. 기다리는 동안 구조(입력·출력 타입, 단계별 내역 형식)를 만들고 규칙은 비워 두세요.

**제약 (모두 필수):**
- **순수 함수**: 같은 입력이면 항상 같은 출력. 파일·네트워크·시간·난수에 의존하지 않음.
- **`Decimal`만** 사용. `float`, `round()`로 만든 금액 금지. 반올림은 허정민 님 규칙(R3)에 적힌 방식·단계만.
- **LLM 호출 금지.** `engine/` 안에서 `openbook.terms`, `openai`, `httpx` 등을 import하지 않습니다 (import 검사 테스트를 추가해도 좋습니다).
- 입력은 **사용자가 확정한 조건**과 정산서 입력뿐입니다. 확정되지 않은 값이 들어오면 거절합니다.
- 출력은 **단계별 계산 내역**(`breakdown`): 각 단계에서 쓴 조건 값, 근거 조항 id, 중간값. 대조 화면이 이 내역을 그대로 보여 줍니다.
- **지원하지 않는 구조는 추정하지 않고 `계산 불가` + 이유**를 돌려줍니다: 구간별 RS(`rs_rate`가 목록), 복수 매체 합산, 필수 조건 누락(`mg_amount`·`rs_rate`·`mg_recoup`·`revenue_base`·`deductions` 중 필요한 것) 등. 목록은 허정민 님 R10 확정을 따릅니다.
- **테스트는 허정민 님의 손계산 JSON 케이스를 그대로 읽어 실행**합니다. 합격선은 **100% 일치**입니다. 하나라도 어긋나면 엔진을 고칩니다 (정답을 고치지 않음 — 정답이 틀렸다고 생각하면 이슈로 허정민 님에게 묻습니다).

### M6 대조·설명 로직

- 차이 = **계약서 기준 금액 − 정산서 금액** (명세서). 부호를 바꾸지 않습니다.
- 단계별 내역과 근거 조항 연결은 **코드가** 만듭니다.
- **결과 문장은 템플릿 문장만 구현합니다.** 형식: `계약서 기준으로 계산하면 ○○원, 정산서에는 △△원, 차이는 □□원입니다.` 숫자는 엔진 출력을 문자열 치환으로만 넣습니다. LLM 다듬기는 선택 사항이고 나중입니다 (정준영 님이 담당하며, 하더라도 숫자는 치환 변수로 전달해 LLM이 바꿀 수 없게 함).
- **금지 표현 필터**를 만듭니다 (`위반`, `부당`, `불리`, `유리`, `위험도 점수`). 필터에 걸린 문장은 템플릿 문장으로 대체합니다. 응답에 나가는 모든 설명 문장이 통과 대상입니다.
- 결과에는 **"플랫폼에 확인할 질문 목록"**을 함께 줍니다.

### 정산서 입력

- 정산 기간, 총매출, 공제 항목, 정산서에 적힌 지급액을 입력받습니다. **같은 계약서에 기간별로 여러 번** 입력할 수 있습니다.
- MVP는 **수동 입력과 표 붙여넣기만** 지원합니다 (정산서 파일 자동 파싱은 제외).
- **붙여넣기 정규화 담당은 정준영 님과 나눕니다.** 형식이 정해지기 전에는 수동 입력부터 구현하고, 붙여넣기 형식은 이슈에서 합의합니다 (허정민 님의 실제 정산서 사례가 기준).

### 삭제 기능 (MVP 필수)

- 사용자가 계약서와 정산 기록을 **삭제**할 수 있어야 합니다. 삭제 시 파일, 조항, 조건, 정산서, 대조 결과, Q&A 기록이 함께 지워집니다.
- 보관 기간은 아직 정해지지 않았습니다 (허정민 님 Q4). 정해지기 전에는 **삭제 기능만** 구현합니다.

## 하지 말 것
- 금액에 `float`을 쓰지 않는다 (DB, 계산, JSON 직렬화 모두)
- 계산 엔진에서 LLM을 부르지 않는다
- 사용자가 확정하지 않은 조건으로 계산하지 않는다
- 계산 규칙이 정해지지 않았는데 추측해서 구현하지 않는다
- 로그·오류 메시지에 계약서 원문을 넣지 않는다
- 스키마(`schemas/`)를 PR·리뷰 없이 바꾸지 않는다
- 결과 문장에 판단 표현을 쓰지 않는다
