# 오픈북 MVP 작업지시서 — 공통 규칙

**모든 팀원이 가장 먼저 읽는 문서입니다.** 담당자별 지시서(`01-`~`04-`)는 이 문서의 규칙을 전제로 합니다.
기준일: 2026-11-14 · 기준 문서: `docs/오픈북 MVP 개발명세서.docx` (2026-11-09)

규칙이 서로 부딪히거나 모호하면 **혼자 판단하지 말고** 해당 이슈에 질문을 남기세요. 추측으로 만든 코드·화면·문구가 이 프로젝트에서 가장 큰 위험입니다.

---

## 1. 우리가 만드는 것

작가가 계약서를 올리면, 서비스가 계약서에서 **MG(선급금)·RS(수익배분) 조건**을 읽어 내 보여 줍니다. 작가가 그 조건을 **직접 확정**하면, 확정한 조건대로 계산한 금액과 **플랫폼 정산서의 금액**을 나란히 보여 주고 차이와 근거 조항을 알려 줍니다.

```
계약서 업로드 → 조항 분할 → 조건 추출 → [사용자가 확인·수정·확정] → 정산서 입력 → 계산·대조 결과
```

서비스는 **판단하지 않습니다.** "계약서 기준으로는 이 금액, 정산서에는 저 금액, 차이는 이것"이라는 사실과 근거만 보여 줍니다. 잘못이 있는지 가리는 것은 이 서비스의 일이 아닙니다.

## 2. 절대 원칙 4가지

이 4가지를 어기면 서비스가 성립하지 않습니다. 코드, 화면, 문구 모두에 적용됩니다.

| # | 원칙 | 이렇게 지킨다 | 이렇게 어긴다 (금지) |
|---|---|---|---|
| ① | **금액·날짜는 코드가 계산한다. LLM은 계산하지 않는다.** | 계산 엔진은 순수 함수, 금액은 `Decimal`만 사용 | LLM에게 금액을 계산·검산시키기, `float` 사용, 프론트에서 금액 계산 |
| ② | **사용자가 확정한 조건만 계산에 쓴다.** | 확정 전 계산 요청은 오류 코드로 거절 | 추출값을 사용자 확인 없이 계산에 사용 |
| ③ | **판단하지 않는다.** | 사실·금액·근거 조항만 표시 | 아래 "쓰지 않는 말" 사용, 위험도 점수·신호등 색으로 좋고 나쁨 표시 |
| ④ | **모르면 지어내지 않는다.** | 못 찾으면 `찾지 못함`, 지원하지 않는 구조는 `계산 불가`와 이유 표시 | 비슷해 보이는 값으로 채우기, 없는 조항 만들기, 추정해서 계산하기 |

### 2-1. "찾지 못함"의 의미 (자주 틀리는 부분)
- `찾지 못함` = **계약서에서 그 조건을 찾지 못했다**는 뜻입니다.
- 이것을 "표준계약서와 같다", "문제없다", "해당 없음"으로 읽히게 쓰면 안 됩니다. 사용자가 그렇게 오해합니다.
- 찾지 못한 조건은 사용자가 직접 입력하게 하고(상태: `직접 입력`), 입력하기 전에는 확정할 수 없습니다.

## 3. 말 규칙

### 쓰는 말
계약서 기준 금액 · 정산서 금액 · 차이 · 근거 조항 · 플랫폼에 확인할 질문 · 표준계약서와 다른 지점 · 찾지 못함 · 계산 불가

### 쓰지 않는 말 (사용자에게 보이는 모든 문장·라벨·버튼·툴팁)
**위반 · 부당 · 불리 · 유리 · 위험도 점수 · AI가 새로 쓴 수정 문구**
- 같은 뜻의 다른 표현도 피합니다 (예: "손해", "불공정", "문제 있음", "안전/위험 등급").
- 색으로도 판단하지 않습니다 (예: 차이가 있으면 빨간색 경고, 없으면 초록색 통과). 차이는 숫자로만 보여 줍니다.

### 결과 문장 형식 (이 문장 그대로, 숫자만 들어감)
> 계약서 기준으로 계산하면 **○○원**, 정산서에는 **△△원**, 차이는 **□□원**입니다.

- 숫자는 계산 엔진 출력을 **그대로** 넣습니다. 반올림·재계산 금지.
- 모든 결과·답변에는 **근거 조항, 기준일, 전문가 상담이 필요한 경우의 안내**를 붙입니다.
- 결과 화면에는 "이 결과는 사용자가 확정한 조건에 대한 계산입니다"를 적습니다.

### 조건 상태 라벨 3종 (이름을 바꾸지 않습니다)
| 화면 표시 | 데이터 값 | 뜻 |
|---|---|---|
| 추출됨 | `extracted` | 계약서에서 찾아 값과 근거를 붙임 |
| 찾지 못함 | `not_found` | 계약서에서 찾지 못함 (값 없음) |
| 직접 입력 | `user_input` | 사용자가 직접 넣은 값 |

## 4. 용어

| 용어 | 뜻 |
|---|---|
| MG | 선급금(최소 보장금). 작가에게 먼저 지급하는 돈 |
| RS | 수익배분(Revenue Share). 매출 중 작가 몫의 비율 |
| 회수 | 먼저 준 MG를 이후 RS 정산액에서 차감하는 것 |
| 총매출 / 순매출 | RS 계산의 기준 매출. 계약마다 정의가 다름 (순매출 = 총매출에서 수수료 등을 뺀 금액) |
| 공제 | 정산 전에 매출에서 빼는 비용(결제 수수료 등) |
| 확정 | 사용자가 추출된 조건을 확인하고 "이 값으로 계산해도 좋다"고 누르는 행위. **사용자만 할 수 있음** |
| 근거 조항 | 그 값을 읽어 낸 계약서의 조항 번호와 원문 인용 |

## 5. 개인정보·보안 (어기면 법적·신뢰 문제)

- **실제 계약서·정산서를 git에 올리지 않습니다.** 로컬 `data/private/`에만 둡니다 (git이 무시함). 샘플은 가상·익명화한 것만 `data/samples/`에 둡니다.
- **API 키는 `.env`에만** 둡니다. 채팅·이슈·PR·코드에 붙여 넣지 않습니다. 노출됐다면 즉시 팀에 알리고 키를 폐기합니다.
- **로그에 계약서 원문을 남기지 않습니다.** 조항 번호와 처리 결과만 남깁니다. 오류 메시지에도 원문을 넣지 않습니다.
- 계약서는 외부 서비스(Upstage)로 전송됩니다. 업로드 화면에서 이를 알리고 **동의를 받아야** 합니다.
- 사용자가 계약서와 정산 기록을 **삭제할 수 있는 기능**이 MVP에 들어갑니다.

## 6. 데이터 형식 규칙

- **금액은 원 단위 `Decimal`입니다. JSON에서는 문자열**로 주고받습니다. 예: `"5000000"`. JavaScript `Number`로 변환해 계산하지 않습니다.
- **비율은 0~1 소수 문자열**입니다. 60% = `"0.6"`. (화면 표시만 `60%`)
- 상태·선택값은 정해진 영문 값을 **정확히** 씁니다 (예: `extracted`, `from_rs`, `net`). 새 값이 필요하면 스키마 PR로 추가합니다.
- 모든 값은 **근거 조항 id와 원문 인용**을 가집니다 (`source_clause_id`, `quote`).
- 스키마의 기준은 `backend/src/openbook/schemas/`이고, 프론트용 JSON Schema는 `docs/schemas/*.schema.json`입니다 (스키마 PR #1 머지 후 사용).
- **실제 응답 예시(목 데이터)**는 `docs/mock/`에 있습니다. 화면·API는 이 모양을 기준으로 만듭니다 → [`docs/mock/README.md`](../mock/README.md)

## 8. Git·협업 규칙

### 처음 세팅 (Windows, Git Bash 기준)
```bash
git clone https://github.com/junyoung0423/openbook-mvp.git
cd openbook-mvp/backend
python -m venv .venv
source .venv/Scripts/activate
pip install -e ".[dev]"
cp ../.env.example ../.env        # 필요한 키는 .env에만 입력
pytest -q                         # 통과하면 환경 준비 완료
```
Python 3.11 이상이 필요합니다.

### 작업 순서
1. 이슈 하나를 맡습니다 (이슈 안의 "끝나는 기준"이 완료 판단 기준).
2. 브랜치를 땁니다: `종류/모듈-내용` 예) `feat/m1-document-parse`, `fix/engine-rounding`, `docs/calc-rules`
3. 작업하고 **자주 커밋**합니다. 커밋 하나에는 한 가지 변경만 담습니다.
4. 올리기 전에: `ruff check .`, `ruff format .`, `pytest -q`가 통과해야 합니다 (backend). CI가 같은 검사를 합니다.
5. PR을 엽니다. PR 템플릿의 체크리스트를 채우고, 본문에 `Closes #이슈번호`를 적습니다.
6. 리뷰어 1명 이상의 확인을 받은 뒤 머지합니다.

### 반드시 지킬 것
- **`main`에 직접 push하지 않습니다.** (이 레포는 플랜 제한으로 시스템이 막아 주지 않으니 사람이 지켜야 합니다.)
- **한 PR에는 한 이슈만.** 큰 PR은 리뷰가 어렵고 오류를 놓칩니다.
- **스키마(`backend/src/openbook/schemas/`)를 바꾸는 PR은 프론트·백엔드 담당 모두의 확인**을 받고, `python backend/scripts/export_json_schema.py`로 `docs/schemas/`도 함께 갱신합니다.
- **남의 브랜치·PR에 말 없이 push하지 않습니다.**
- CI가 실패한 PR은 머지하지 않습니다.
- 비밀값·실제 계약서가 커밋에 섞였다면 **바로 팀에 알립니다** (지우는 것만으로는 이력에서 사라지지 않습니다).

## 9. 완료의 정의

"끝났다"고 말하기 전에 아래를 모두 확인합니다.
- [ ] 이슈의 "끝나는 기준" 항목을 전부 채웠다
- [ ] 테스트(백엔드) 또는 직접 실행(프론트·디자인 산출물)으로 동작을 확인했다
- [ ] 위 "절대 원칙 4가지"와 "말 규칙"을 어기지 않았다
- [ ] 실제 계약서·정산서·API 키가 변경분에 없다
- [ ] PR 본문에 **무엇을 했는지, 무엇을 확인했는지, 무엇을 못 했는지**를 솔직하게 적었다 (못 한 것을 적는 것은 감점이 아닙니다)

## 10. 막혔을 때

1. 이슈를 다시 읽고, 이 문서와 담당자별 지시서를 확인한다.
2. 1시간 이상 막히면 **이슈에 질문을 남깁니다.** 무엇을 하려 했는지, 무엇이 안 됐는지, 에러 메시지(원문·키 제외)를 적습니다.
3. 정해지지 않은 사항(예: 반올림 규칙, 정산서 붙여넣기 형식)을 **임의로 정하지 않습니다.** 이슈에 "결정 필요"로 올리고, 결정되기 전에는 그 부분을 비워 두거나 가장 단순한 안전한 동작(거절, `계산 불가` 표시)을 합니다.

## 11. MVP 범위

**포함 (P0)**: 계약서 업로드·조항 분할 / MG·RS 조건 추출과 사용자 확정 / 정산서 입력(직접 입력, 표 붙여넣기) / 계약서 기준 계산과 정산서 대조, 근거 조항 표시
**포함 (P1)**: 표준계약서 비교 요약, 조항 Q&A
**포함 (P2, 뒤로 미룸)**: 수정 요청 목록, 정산일 알림
**MVP에서 제외**: Word 추가기능, 정산서 파일 자동 파싱, 네이티브 앱, 결제, 미수금 대응, 세금 관리, 웹툰·웹소설 외 업종 확장, 자동연장·2차 사업 카드
**계산 불가로 처리 (지원 안 함)**: 구간별 RS는 스키마(RsTier)에 구간 표현이 있지만, MVP에서는 계산하지 않고 '계산 불가'로 둔다. 복수 매체 합산은 스키마에 매체 개념이 없고 MVP 범위도 아니다.

> **범위 축소 제안 (허정민 확인 후 확정)**: 조항유형 세분화(`clause_types.yaml`) 보류, 결과 문장은 템플릿 문장만(LLM 다듬기 제외), Q&A는 사용자 계약서만 검색. 확정 전에는 **지금 지시서대로** 진행하고, 확정되면 이 문서와 이슈를 갱신합니다.

> **LLM 비교 재측정 보류 (2026-11-20 결정)**: 명세서 7절의 "같은 60문항을 실제 LLM 답변으로 재측정"은 보류합니다. 2026-10-26 평가에 쓴 가상 계약서 10건과 60문항 정답지가 남아 있지 않습니다 (저장소에 없고 허정민 님도 갖고 있지 않음).
> - 따라서 명세서 성공 기준 4번(다른 지점 탐지 재현율 85% 이상, 핵심 조항 재현율 90% 이상)은 **확인 안 됨** 상태입니다. 통과한 것으로 쓰지 않습니다.
> - 비교 기능(P1)은 그대로 만듭니다. 인용은 코드가 원문과 대조하고, 못 찾은 항목은 "찾지 못함(표준과 같다는 뜻이 아님)"으로 표시합니다.
> - 비교 기능의 정확도는 사업계획서·발표·화면 어디에도 쓰지 않습니다.
> - 다시 할 때: 새 가상 계약서 세트와 정답지를 만들고, 합격선을 실행 전에 커밋한 뒤 측정합니다. 정답지는 허정민 님이 검수합니다. 데모나 발표 전에 시간이 나면 진행합니다.

## 12. 현재 AI 파이프라인 상태 (정준영)

- M2 조항 분할: 구현됨. `제N조`, `N.` 형식 지원. 못 나누면 `clause_review_needed=True`.
- M4 조건 추출: 구현됨. LLM 답을 코드가 검증해서 통과 못 한 값은 `찾지 못함`으로 둠. 한글 금액("오백만 원")은 읽지 않고 `찾지 못함` 처리.
- 알려진 한계: 가상 샘플 2건으로만 확인했습니다. **실제 계약서 정확도는 모릅니다.** 실제 사례가 확보되면 합격선을 정하고 측정합니다.
- M3 표준계약서 비교: 구현됨 (PR #16·#21, 머지 전). 정산 관련 핵심 6개 조항을 비교합니다. **탐지 재현율은 측정하지 않았습니다** (위 11절 보류 참고).
- 서로 충돌하는 정의(예: 한 조항은 순매출, 다른 조항은 총매출 기준 공제)는 코드가 찾지 못합니다 → **조건 확인 화면에서 사용자가 원문을 보고 고르게 해야 합니다.**
