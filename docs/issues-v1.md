# 이슈 초안 v1

GitHub Issues에 하나씩 등록한다. 제목은 그대로, 본문은 아래 "목표"와 "끝나는 기준"을 붙여 넣는다.
라벨은 처음 한 번 만든다: `M1`~`M8`, `frontend`, `design`, `기획`, `P0`, `P1`, `P2`.
담당은 명세서 9절 기준이며, 팀에서 바꾸면 이 파일도 고친다.

작업 순서는 **1단계(지금 시작) → 2단계(스키마 PR 머지 후) → 3단계(입구·마감)** 이다.

---

## 1단계 — 뼈대

### 허정민

**[기획] 사례 계약서·정산서 확보와 익명화** · `기획` `P0`
- 목표: MG·RS 조건 추출과 계산을 검증할 실제 또는 사례 계약서·정산서를 모은다.
- 끝나는 기준
  - [ ] 확보한 건수와 출처를 팀에 공유 (익명화 조건 포함)
  - [ ] 실제 자료는 `data/private/`에만 두고 커밋하지 않음
  - [ ] 가상 사례는 `data/samples/`에 둠

**[기획] MG·RS 계약 유형 분류** · `기획` `P0`
- 목표: 첫 대상 분야에서 실제로 나오는 MG 회수 방식, 매출 정의, 미회수분 처리 유형을 정리한다.
- 끝나는 기준
  - [ ] 유형 목록 문서 (`docs/`)
  - [ ] 스키마 선택지 확정: `mg_carryover`, `settlement_cycle`, `mg_pay_date`, `payment_day` 형식
  - [ ] 구간별 RS와 복수 매체 합산을 MVP에 넣을지 결정

**[기획] 계산 규칙 명세서와 손계산 테스트 케이스** · `기획` `P0`
- 목표: 계산 엔진(M5)의 완성 기준이 될 규칙과 정답 케이스를 만든다.
- 끝나는 기준
  - [ ] 계산 규칙 명세서 (`docs/`)
  - [ ] 손계산 케이스: MG 회수 전, 회수 중, 회수 완료, 공제 포함, 매출 0원인 달
  - [ ] 입력과 기대 출력이 JSON으로 정리됨

### 정준영

**[M2] 규칙 기반 조항 분할** · `M2` `P0`
- 목표: 계약서 텍스트를 번호·제목 규칙으로 `Clause[]`로 나눈다.
- 끝나는 기준
  - [ ] `data/samples/` 샘플에서 조항 개수·번호가 기대값과 일치 (pytest)
  - [ ] 규칙이 실패한 문서를 구분해 알려 줌 (LLM 보완 대상)

**[M2] `clause_types.yaml` 초안 15~20개** · `M2` `P0`
- 목표: 조항유형 체계를 만든다. 정산 계열(MG, RS율, 공제, 회수, 정산 주기)을 가장 잘게 나눈다.
- 끝나는 기준
  - [ ] YAML 파일과 로더, 유형 id 검증 테스트
  - [ ] 허정민 님과 유형 이름·범위 합의

### 박다연

**[M1] Postgres 설정과 DB 모델** · `M1` `P0`
- 목표: 명세서 5절 테이블(users, contracts, clauses, terms, statements, reconciliations, qa_logs, alerts)을 만든다.
- 끝나는 기준
  - [ ] 로컬 실행 방법 문서화 (Docker 또는 설치)
  - [ ] 금액은 NUMERIC으로 저장
  - [ ] 마이그레이션 도구 선택 (팀 합의)

**[M1] Upstage Document Parse 연동** · `M1` `P0`
- 목표: 파일을 읽어 정규화 텍스트와 요소 위치로 돌려주는 모듈을 만든다. 파서를 나중에 바꿀 수 있게 인터페이스를 고정한다.
- 끝나는 기준
  - [ ] PDF, docx, HWP, 이미지, 붙여넣은 본문 입력
  - [ ] 출력: 문단·표·목록 구조 텍스트와 요소 위치
  - [ ] 실패·타임아웃 처리, 로그에 계약서 원문을 남기지 않음

### 신민주

**[FE] Next.js 세팅과 업로드 화면 (목 데이터)** · `frontend` `P0`
- 목표: `frontend/`에서 실행되는 Next.js + TypeScript + Tailwind 앱과 업로드 화면을 만든다.
- 끝나는 기준
  - [ ] `npm run dev` 실행
  - [ ] 목 데이터로 업로드 → 조항 확인 화면까지 이동
  - [ ] 스키마 PR이 머지되면 `docs/schemas/*.schema.json`으로 타입 생성

### 전시준

**[디자인] 전체 흐름 와이어프레임** · `design` `P0`
- 목표: 업로드 → 조항 확인 → 조건 확인 → 정산서 입력 → 대조 결과 흐름의 와이어를 만든다.
- 끝나는 기준
  - [ ] 조건 확인 화면에 추출됨 / 찾지 못함 / 직접 입력 상태와 근거 조항 원문이 한 화면에 보임
  - [ ] 대조 결과 화면에 계약서 기준 금액, 정산서 금액, 차이, 근거 조항이 보임
  - [ ] 위반·부당·불리·유리 같은 판단 표현을 쓰지 않음
